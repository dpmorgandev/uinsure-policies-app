Docket UI User Guide

The explorer and the workbench: every screen, every workflow, with screenshots, numbered steps and highlighted regions. For assessors, developers and users of the Uinsure Policies build.

Short form: cut to a short form on 2026-10-23 for time. The web app is not on this guide's branch yet (F8). Every src/Uinsure.Policies.Web path resolves on feature/ui/U10, and on main once the ui plan merges.

The big ideas

  1. Two halves. The explorer reads the build trail (trace.json); the workbench drives the API with real requests.
  2. Evidence. Every rule, node, commit, verdict and finding has a page and a deep link, from the requirement to its tests and commits.
  3. Honest. A missing value is drawn as missing, an API answer is shown with the status the page received, and nothing is invented.
  4. Regions. Each section of a screen carries a data-region tag; the numbered markers in this guide are measured from those tags.
  5. Contracts. Screens were agreed as static HTML first and the app is tested against them: unit, end to end, axe, parity and visual regression.
  6. Run it yourself. Every test collection can be run by hand: Postman, Playwright, Vitest.

1. What Docket is

Docket is one app with two halves: an explorer for the build trail and a workbench for the API.

The explorer reads trace.json, compiled from git and the trail files, and shows rules, plans, nodes, commits, verdicts and findings. The workbench sends sell, quote, cancel, claim and renew requests to the running API and shows the answers. Both are static pages with hash routes.

2. Run it

Build once, preview it, and point /api at the API.

The static build is served by vite preview; the workbench calls /api/... and the app proxies it to the API port in DOCKET_API_PORT (default 5080). The dev server does the same on port 4170, which is what the Visual Studio launch profile starts beside the API.
