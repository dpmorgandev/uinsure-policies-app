Docket UI User Guide

Two people's journeys through Docket: a policy servicer in the workbench, and an assessor in the explorer. At every step you see what you decide, what Docket gives you back, the control to use boxed in red, and the result it produces.

Screenshots come from the app on main, with the trail compiled at snapshot a2dc6df. Every path is under src/Uinsure.Policies.Web or tests/Uinsure.Policies.Web.Tests.

The big ideas

  1. Two people. A policy servicer drives the API from the workbench; an assessor checks how it was built from the explorer. Pick your journey and follow it.
  2. Decide, then see. Every step names what you decide and what Docket gives you back, so the screen is never a surprise.
  3. Red boxes. The control a step drives from has a red box and a "Step n" label. The shot shows the result the step produces.
  4. Evidence. Every rule links to its requirement, its tests, its commits and its verdicts, so one click replaces a search of the git log.
  5. Honest. A missing value is drawn as missing, an answer is shown with the status the page received, and nothing is invented.
  6. Contracts. Screens were agreed as static HTML first, and the app is tested against them: unit, end to end, axe, parity and visual regression.
  7. Run it yourself. Every test collection can be run by hand: Vitest, Playwright and Postman.

Start here

Pick your journey, then follow its steps in order.

Docket is one app with two halves. The workbench sends real requests to the API and shows what came back. The explorer reads the build trail and shows how each rule was proved. Each half has its own journey below, and each step in a journey follows the same shape.

How to read a screenshot

A red box is drawn round the control or region a step drives from, with a red "Step n" label beside it. The sub-step list under the shot says what to do at "Step n". A shot with no box frames a result: the response, the end of a page, a plan picture. Box positions are measured from each region's data-region tag by capture.mjs, never placed by eye.

Two kinds of Step Explorer screens print their own rung labels in black, such as Step 1 Read the answer. Those belong to the screen. The red Step n labels belong to this guide. Where a screen prints its own labels, the step text says which one it means. The workbench forms print numbered circles for their rungs; they are not boxes or labels either.
Why Choice: Box each control from the app's own region tags. Alternative: Place boxes by hand. Reason: A hand-placed box drifts when the layout changes. A measured box cannot lie about where a tagged region is.
Untagged regions Four regions carry no data-region tag: the header and theme toggle, the cancel confirmation dialog, the requests drawer, and a problem banner inside a screen. Their boxes are measured from the element found by its accessible name, and the manifest records the nearest tagged ancestor. Nothing is placed by hand.

Journey 1: the policy servicer, in the workbench

From opening the workbench to a cancelled policy, a claim, a refused renewal and the requests behind them.

You sell a policy, read it, quote a cancellation and cancel, record a claim, try a renewal, and read the requests you sent. At each step the workbench shows the status the API answered, never one it did not receive. Forms validate as you go, the refund is shown before you commit, every call is logged with a curl, and the rule behind each refusal is one click away.

    The kit and its tokens

    src/Uinsure.Policies.Web/kit holds the primitives, patterns and layouts that every screen is built from, with tokens/tokens.css for colour, type and spacing. This guide uses the same tokens, copied unedited into docs/guides/assets. kitchen-sink.html shows every component.

    The design pipeline, and why screens are contracts

    docs/ui holds the pipeline: directions, concept, styles, mockups, then one static HTML per screen state in docs/ui/screens, with signed-off shots in docs/ui/screens/_shots and baselines in docs/ui/baselines.

    Why Choice: Agree each screen as static HTML first, and test the app for parity against it. Alternative: Design in the code. Reason: A reviewer can approve a screen without reading React, and a test fails when the app drifts from it.
