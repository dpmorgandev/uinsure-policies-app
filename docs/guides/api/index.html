Uinsure Policies API
User guide

Two journeys through the API: a developer joining the project, who clones, runs, tests and learns where a rule lives, and a servicer who drives the API directly with curl and Postman. At every step you see what you decide, what the repository or the API gives you, and the real output it produces.

Every command in this guide was run on the feat-001/N1 branch on 2026-10-25, and every output, count and test number is copied from that run (receipts.md, next to this guide's source).

The big ideas

  1. A policy has a life. It is sold, is pending or active, can be renewed in its last 30 days, and ends cancelled or expired. Its status is worked out from today and never stored.
  2. Four projects, one direction. The domain holds every rule and needs only .NET. Services orchestrate, Persistence stores, the Api speaks HTTP. Architecture tests enforce who may reference whom.
  3. One pipeline. Every request passes the same stages, from forwarded headers to the repository. One injected clock decides "today", and one method rounds money.
  4. Errors come in order. A 400, 404 or 409 is returned alone. Only then are all the 422 rules checked together. Every failure is one RFC 9457 body that names the rule.
  5. A cancellation is a decision. Five outcomes decide the refund, and the response names the one that applied in ruleApplied.
  6. Each test proves something different. Domain, Services, Api, Architecture, the web suites and Postman each catch a different kind of mistake. Every rule ID is a test trait.
  7. Test first, shipped as evidence. Outside-in TDD built it and left a trail. The Bicep and the pipeline were built and checked locally and never deployed.

    Why, in six decisions

    Why Terms, not overwritten dates. The alternative was to move the policy's dates on renewal. Renewal happens while the old term still runs, so overwriting would break a cancellation made in its last 30 days (RENEW-4).
    Why One result type and one status mapping. The alternative was exceptions per rule, with status codes chosen in controllers. A Result lets the domain report every broken rule at once, and ProblemCatalog is the only place a status is chosen.
    Why Interfaces only at the layer seams. The alternative was an interface per class, a generic repository and a mediator. Three seams (service, repository, reference generator) are what the tests need; more would be speculation.
    Why No DateTime.Now. The alternative was to read the clock where needed. One injected clock makes every date boundary testable, and the build fails on the banned calls.
    Why SQLite locally. The alternative was SQL Server in a container. SQLite needs nothing installed, so the reviewer runs the API in a minute; the provider switch is a configuration key.
    Why Rounding in one method. .NET rounds halves to even by default. The brief's pro-rata refunds need half away from zero, so it is chosen once in Money.Round (CANCEL-6). And evidence instead of a deployment: the brief put live deployment out of scope, and an unrun pipeline can claim only what a local check proved.
