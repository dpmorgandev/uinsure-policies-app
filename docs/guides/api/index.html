Uinsure Policies API
User guide

Run it, call it, test it and understand it. For the assessor, the developer who joins the code, and the person who calls the API.

Every command in this guide was run on the F7 branch on 2026-10-23, and every output, count and test number is copied from that run (receipts.md, next to this guide's source).

The big ideas

  1. Rules have IDs. Every rule in the brief has an ID (SELL-2, CANCEL-1b) in docs/requirements.md. The same ID is a test trait, a code comment and the ruleId in an error body.
  2. Terms. A policy is a list of terms. A renewal appends the next term and never overwrites dates, so a cancellation made in the last 30 days still works.
  3. One clock. "Today" is the UK date, computed once from an injected TimeProvider in Europe/London. The domain only ever receives a DateOnly.
  4. One error shape. Every failure is an RFC 9457 problem body. A 400, 404 or 409 is returned alone. A 422 lists every broken rule.
  5. One rounding. Money is rounded in one method, Money.Round: 2 decimal places, half away from zero.
  6. Prove it. 637 tests in four projects and a Postman collection of 253 requests, all green on this branch. Each rule has a unit test and an HTTP test.
  7. Evidence, not deployment. The Bicep and the Azure DevOps pipeline were built and checked locally and never deployed.

1. What it is

A REST API that sells, retrieves, cancels, renews and records claims on home insurance policies.

It is the take-home for Uinsure's senior engineer role. The brief asked for the sell, retrieve, cancel and renew operations. All of its MUST, SHOULD and COULD rules are built, plus a cancellation quote and claims. Each rule has an ID and one agreed interpretation in docs/requirements.md. Where the brief was unclear, the interpretation is written down, not guessed.

Where the brief was unclear

The full list is the assumptions section of the README (README.md:151). The ones that change what you see:

What is deliberately not done

Out of scope
  1. Authentication. The reference is the only key, so anyone who guesses it can read the policy or post a claim.
  2. Pricing (the client sends every amount) and real payment processing.
  3. Live deployment. The Azure files are evidence (section 6).

The known limits, including the security scope, are in docs/design.md and the README's "Known limits".

The SQLite and SQL Server switch

The reference in the path is trimmed and upper-cased, so a lower-case one finds it. status is derived from today: Pending before the first start, Active, Expired after the last end, and Cancelled, which overrides the rest. The policy-level dates and amount describe the current term.

Quote, then cancel

COULD-1, CANCEL-1a to CANCEL-7. Quote first: GET …/cancellation-quote?cancellationDate=yyyy-MM-dd changes nothing. Then POST …/cancellation; the body is optional, and cancellationDate defaults to today. Each refund goes back to the method of the payment it reverses (CANCEL-2).

Cancelled onruleAppliedRefund
Before the start dateCANCEL-1aFull amount
Start date to start + 14 days, inclusiveCANCEL-1bFull amount
LaterCANCEL-1cAmount × unused days ÷ days in the term
The policy has a claimCOULD-20.00, whatever the date
The term was never paid (an unpaid renewal)UNPAID-TERM0.00, and it wins over a claim

Renew a policy

RENEW-1/2 to RENEW-6, COULD-3. POST …/renewals takes the new term's amount and, optionally, a paymentMethod. You may renew from 30 days before the latest term's end date to the end date, both inclusive. The new term starts the day after the end. With autoRenew on, the payment method defaults to the current term's, and a Cheque is refused. With it off, the term is created unpaid and a paymentMethod is refused.

  1. Renew the policy sold today (GUIDE-002), which ends 2027-10-22. 
    curl -s -i -X POST http://localhost:5080/policies/GUIDE-002/renewals -H "Content-Type: application/json" -d '{"amount":1250.00}'
    422: RENEW-1/2. The window is named in the body.

Every body follows RFC 9457. type is /problems/ and the rule ID in lower case, with / as -. ruleId names the rule, violations[] lists every broken rule on a 422, and traceId finds the request in the logs. One place maps a rule to its status, type and title.

Why, in six decisions

Why Terms, not overwritten dates. The alternative was to move the policy's dates on renewal. Renewal happens while the old term still runs, so overwriting would break a cancellation made in its last 30 days (RENEW-4).
Why One result type and one status mapping. The alternative was exceptions per rule, with status codes chosen in controllers. A Result lets the domain report every broken rule at once, and ProblemCatalog is the only place a status is chosen.
Why Interfaces only at the layer seams. The alternative was an interface per class, a generic repository and a mediator. Three seams (service, repository, reference generator) are what the tests need; more would be speculation.
Why No DateTime.Now. The alternative was to read the clock where needed. One injected clock makes every date boundary testable, and the build fails on the banned calls.
Why SQLite locally. The alternative was SQL Server in a container. SQLite needs nothing installed, so the reviewer runs the API in a minute; the provider switch is a configuration key.
Why Rounding in one method. .NET rounds halves to even by default. The brief's pro-rata refunds need half away from zero, so it is chosen once in Money.Round (CANCEL-6).

7. How it was built

Test first, in a loop, with a recorded trail for every feature.

AI agents in Claude Code built this repository inside a harness, with a human deciding at fixed points. Every rule in the brief got an ID; every feature is a node in a plan; every node leaves a trail of commits, verdicts and findings.

Counted from docs/trace/build/ on this branch, the nodes F0a to F6 hold 15 findings (in seven of the nodes), and the reviewer and security verdict files number 51 (F0b 5, F1 4, F1b 4, F2 6, F3 6, F4 6, F5 12, F6 8). A finding sends a node back through the failure route: diagnose, write a new red test, then fix. The third failure stops for a written investigation.

The full story, with each node's walkthrough and every finding, is browsable in Docket, the web app, which the UI guide covers.
