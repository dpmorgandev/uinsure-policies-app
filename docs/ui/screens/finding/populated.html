  1. I1 · rule COULD-2 · layer api · attempt 2 · testable

    I1FixedTestable

    Symptom
    live POST /policies/{ref}/claims returns 500 with an InvalidOperationException saying RecordClaimRequest has validation metadata on record property 'Description' that will be ignored.
    Cause
    CancellationContracts.cs:38-40 declares RecordClaimRequest as a positional record and targets its DataAnnotations at the generated properties ('[property: Required] DateOnly? ClaimDate' at :39 and '[property: MaxLength(500)] string? Description' at :40). MVC builds a positional record through its primary constructor, so it reads validation metadata from the constructor parameters. When it finds validators on a property that maps to a constructor parameter, it throws during object-model validation instead of quietly ignoring them. The throw happens on every request whose body deserialises into a RecordClaimRequest (PoliciesController.cs:63 binds it from the body), so the happy path, 404, 422 and DataAnnotations-400 cases all become 500s. The stub's canned body at :65 never runs. The exception names only 'Description', but ClaimDate at :39 has exactly the same pattern and is the same cause (not a separate finding). Fixing only :40 would probably just move the exception to ClaimDate; the code doesn't show why MVC reported Description first. COULD-2 says 'claimDate required, description optional, max 500', and the architecture contract says required DTO members are 'nullable and [Required]'. Both constraints have to be enforced as a 400, not dropped or turned into a 500.

    src/Uinsure.Policies.Api/Contracts/CancellationContracts.cs src/Uinsure.Policies.Api/Controllers/PoliciesController.cs
    Fix direction
    put the Required and MaxLength(500) constraints where MVC reads them for this type. Either attach them to the record's constructor parameters, or make the contract a class with settable properties, like the existing SellPolicyRequest (SellPolicyRequest.cs:20, a class whose [Required]/[MaxLength] attributes are on properties). Keep both members nullable. Other F3 request contracts checked, not affected: CancelPolicyRequest (CancellationContracts.cs:6) is a positional record with no validation attributes, so nothing triggers the check, and the gate saw cancel answer 201 live. The quote has no request record: its only constraint is '[FromQuery, Required]' on the action parameter at PoliciesController.cs:51, and action parameters are not subject to this check, so the gate saw quote answer 200 live. The response records (CancellationContracts.cs:8-36, 43-48) carry no DataAnnotations and are never model-validated.
