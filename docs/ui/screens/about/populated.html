Step 1

Read the labels

Each value on the other screens carries one of these three labels. The label says who produced the value. Read it before you weigh the value.

generateda hook or render-trace.mjs wrote it, never an agent producing the code

The compiled-at stamp in the header above is generated.

recordeda hook stored an agent's judgement verbatim; the agent can't alter it afterwards

A reviewer or security verdict is recorded: you read the agent's own words, not a summary of them.

writtenby David or the main session

Text authored by a person or the main session carries this label. Read it as a claim made by its author, not as a measurement.

Step 2

Look up the terms

A status is always a word, a glyph and a colour. Colour is never the only signal.

Pass

What was counted or checked passed. A count says what it was counted from.

Fail

A recorded check or verdict failed. It keeps its own rung and is never folded into a count.

Warn

A gap or disagreement in the trail. Read the sentence beside it before relying on the value.

Pending

Not done yet, so there is nothing to check yet.

Not built

Not built yet. There is no red, green, refactor, QA step or sign-off to show, and the page says so instead of inventing one.

Terms used on the other screens.

  • Rung. One numbered step in a story. The number is the step's position in the order, not a time.
  • Red, green, refactor. The values of a commit's TDD trailer. A rule page puts the red commit above the green one, so you read the order from position.
  • Attempt. One pass of a node through the build loop. Every attempt keeps its own rung; retries are never folded into a counter.
  • gate.stub. A recorded check, shown with what it expected and what it returned.
  • Verdict. A reviewer's or security agent's PASS or FAIL, recorded verbatim.
  • Finding. A problem a verdict raised. A later commit's Fixes-Finding trailer names the one it fixes.
  • Human decision. A point where David approved, steered or merged. They are listed together on the Human decisions screen.
  • Git-only. A node with no trail files; what is shown comes from git alone.
  • Snapshot. The commit this site was compiled from, stamped in step 5.

Step 3

Re-run it in git

You do not have to trust this site. Each command below runs in a clone and prints what git itself holds. Run them in this order.

First, confirm the snapshot commit exists.

Run this in a clone. It asks git what kind of object the stamp's SHA is.

git cat-file -t b394466f9e89d823fbe13a904ab45296d782b033

Expect commit.

The SHA is the one in the compiled-at stamp (step 5); the page has no recorded output for it.

Then re-check an order. The command lists commits oldest first, each with its TDD trailer. A rule page gives its own red and green SHAs; the two below are the kit's specimen pair, not part of this page's data.

Run this in a clone. It lists the commits from the red SHA to the green SHA in the order they were made, with each one's TDD trailer.

git log --reverse --format="%h %(trailers:key=TDD,valueonly) %s" 94a7473^..92ede9e

Expect 94a7473 first with trailer red and 92ede9e last with trailer green.
