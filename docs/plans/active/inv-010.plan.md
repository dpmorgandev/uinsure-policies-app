# inv-010: N1's listen-first server meets a shell that reads trace.json once
## Question
Why does bug-002/N1 FAIL review at attempt 2 (R1: F5 lands on "trace.json could not be read (HTTP 503)" while the trail compiles), and is the cause in the listen-first design, in the shell's one-shot trace load, or in tests that never open the page during the compile?
## Hypothesis
Listen-first (35122e4b) moved "ready" from port-bind to compile-end, but Vite's --open fires on listen, not on printUrls, and the shell loads trace.json once and treats a 503 as terminal; no test drives a page against the dev server during the compile. Disproved if Vite opens only after printUrls, if the shell already retries a 503 "compiling", or if a test opens the page mid-compile.

## Findings
**Yes, all three, with one cause and one trigger.** The cause is the shell's one-shot load: the only reader of /trace.json treats every non-2xx answer as final and asks once. Listen-first's open-on-listen is the trigger, and no test opens a page during the compile. Seven findings, all new; none shares a fingerprint with A1. Details in [findings/A2.md](../../trace/bug-002/N1/findings/A2.md).
- I1 (new, DATA-1, blocking): `app/data/trace.ts:245-265` turns the compiling 503 into a final error, and `app/shell/Frame.tsx:41-53` never asks again. Vite opens the browser inside listen() (`vite.config.ts:49-50` holds back only the "Local:" line), and an open tab reloads on reconnect. Every path that loads the page mid-compile hits it.
- I2 (new, DATA-1): `Docket.Web.esproj:4` StartupCommand `npx vite` bypasses the `scripts/dev.mjs` guard. The shipped "API and web" F5 runs the DebugTarget, not this (`Uinsure.Policies.slnLaunch:11-13`, `LaunchProfileTests.cs:69-71`), but it is still a launch path the plan names.
- I3 (new, DATA-1): `vite.config.ts:53` decodes every request URL before the /trace filter, so a malformed escape on any path is a 500.
- I4 (new, API8:2023): `vite.config.ts:56-58` accepts a directory, so GET /trace/ throws EISDIR and answers 500.
- I5 (new, DATA-1): `data-1-first-run.test.ts:218` matches /compil/i, which both 503 bodies satisfy. The two states differ only in prose, which I1's fix must not key on.
- I6 (new, DATA-1, prose): `data-1-trace-on-start.test.ts:2-5, :147` still describe compile-first.
- I7 (new, DATA-1, blocking): `LaunchProfileTests.cs:85` still pins the old program, so the .NET suite fails at HEAD and pre-push would refuse the branch. The gates ran npm only.
