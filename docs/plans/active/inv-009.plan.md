# inv-009: What main still holds after #121
## Question
Does main, after #121, still hold unfinished or defective work (a plan node not done, a carry-over or deferred finding that no node closes, a first-run gap where a fresh clone can't F5 straight into Docket, a Docket region still marked "not built yet", or a workbench interaction that doesn't show the request it sent and the response it got), and if so which items?
## Hypothesis
Yes, in four groups:
- **(a) First run.** Nothing in the VS launch path restores `node_modules` or opens Docket, and the trace compile blocks Vite's start.
- **(b) Placeholders.** The "request as sent" inspector regions on Sell and Cancel were never given to a node.
- **(c) Workbench defects.** The Send result is read from a field the screen's data doesn't hold, the JSON is printed without indentation, and the request view is cleared after sending.
- **(d) Plan state.** No commit moved F7, F8 or U10 to done.

Each part is disproved by code on main that already does the thing, or by DAG statuses that already read done:
- an npm restore in the launch path, or a launch that opens Docket
- a built inspector region
- a Status bound to the response
- indented JSON

## Findings
**Yes.** Main still holds unfinished and defective work. 22 of the 24 findings are real on main. I3 follows from I1 and I4, and I2 is IDE state. Hypothesis (a) holds except for "nothing opens Docket": the Vite target already passes `--open`. Hypothesis (c) is wrong on mechanism in two places: Status is never bound at all, and nothing is cleared after a send. (b) and (d) hold. The investigator ran standalone, so no findings file was filed. Every finding's id, cause and file:line is copied here.

**First run: what a reviewer who clones the repo hits first**
- I1 (new): nothing in the F5 path restores packages. `Uinsure.Policies.slnx:48-50` sets the esproj to `Build Project=false`. `Docket.Web.esproj:1-10` has no restore step. `.vscode/launch.json:9` runs `node_modules/vite/bin/vite.js` directly. The only restore is a prose instruction at `README.md:21`. No node owned it: U9 kept npm out of the build (`ui.dag.yaml:552`), and U10's one-key F5 (`ui.dag.yaml:591`) assumed node_modules already existed.
- I2 (new, not a repo defect): VS keeps the active launch profile per user in `.vs/` (`.gitignore:5`). The repo ships the profile (`Uinsure.Policies.slnLaunch:3`) and the README line (`README.md:16`).
- I3 (no cause of its own): the Vite target already passes `--open` (`launch.json:10`, pinned by `LaunchProfileTests.cs:94-98`). Vite opens the browser only once it's listening, which never happens on a fresh clone (I1) or happens only after the compile ends (I4).
- I4 (new, DATA-1): `vite.config.ts:37-42` runs the whole trail compile synchronously in Vite's config hook, so the port isn't bound until the compile returns. The compile spawns one `git` process per blob and per commit (`compiler/index.ts:164-168`, `:190`, `:331-332` via `git.ts:37-39`, `:53-55`). U10's trace-on-start line (`ui.dag.yaml:594`) set no time budget.
- I5 (new, environment): jsdom and react-router (`package.json:22`, `:35`) need a Node newer than 22.18. The README states 22.22+ (`README.md:110`), but `package.json` has no `engines` field and the repo has no `.nvmrc`.
