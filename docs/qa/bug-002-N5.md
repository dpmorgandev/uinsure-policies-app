## What changed in N5

- **A null holder is a shape error.** On main, `"policyholders": [null]` or `[{…}, null]` reached the mapping and
  threw, so the API answered 500. Now `SellPolicyRequest.Validate` reports each null element as
  `policyholders[<index>]`, with the message `A policyholder must not be null.`. MVC stops on the invalid model state,
  so the request is never mapped and nothing is stored.
- **It's a 400, not the 422 SELL-4.** SELL-4's 422 is about the count, 1 to 3 holders, and that rule is unchanged.
  A null element isn't a holder at all, so it's caught at the 400 level, before any 422 rule runs. A body of four
  nulls is four 400 errors, not a 422.
- **The API has a version.** The API csproj declares `<Version>0.1.0</Version>`. An OpenAPI document transformer sets
  `info.version` from the assembly's informational version, with the `+<commit>` suffix cut off. On main the
  document said the generator's default, `1.0.0`. `0.1.0` was the builder's choice: pre-1.0, because the contract
  isn't public yet, and visibly different from the default.

## Notes

1. **The version test carries the SELL-4 trait, but it isn't about SELL-4.** It's traited SELL-4 only so the node's
   rule filter runs it. The reviewer raised this as R1 (P2, not blocking): it's plumbing, and it counts towards
   SELL-4's integration coverage without proving the 1-to-3 rule. SELL-4 has its real rows in the count tests above.
   Steps 1 and 2 hold SELL-4 in the Rule column for the same reason. If you'd rather it carried no trait, that's a
   steer for this node.
2. **One error per null, with no cap.** Step 8 shows a body with two nulls gets two errors. Security raised S1 (P2,
   API4, not blocking): a 64 KB body of nulls gets an error per element back, so the response is a few times bigger
   than the request. The 64 KB request cap and the rate limiter bound it. N6's first acceptance line documents it in
   the API guide. Step 8 isn't backed by its own test: I read the expected result from `SellPolicyRequest.Validate`.
3. **A null holder never reaches SELL-4's count.** `[null]` is one element, but it's a 400, not a sold policy with
   one holder or a 422. A body like `[null, h, h, h]` gives the 400 `policyholders[0]` alone, not the 422 for four
   holders, because the 400 level comes first (the evaluation order in the architecture contract). No step or test
   checks that combination. If you want one, it's a steer.
4. **What I saw and what I didn't.** I haven't run these steps or the Postman collection, and no gate in this node
   recorded a Postman run. I read the expected text from `SellPolicyRequest.cs`, `Program.cs` and the API csproj at
   f0ba7dd0, from the two tests and the two Postman requests added in 713f64d9, and from `ProblemAssert.cs`.
   `gate.run` at 4e8400af recorded `/openapi/v1.json` `info.version` `0.1.0` and `[null]` → 400 against the
   running API. The `+<commit sha>` suffix on ProductVersion in step 2 depends on the SDK's source-revision setting,
   which I haven't checked. The error message in steps 3 and 6 is the code's string, and the tests don't assert it.
