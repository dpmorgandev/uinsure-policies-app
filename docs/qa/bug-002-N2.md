## What changed in N2

- **Sell and Cancel draw the drawer in their inspector region.** Main draws the not-built-yet placeholder there. On
  sell, the region is headed "Receipt for rung 4: what was sent, what came back". On cancel, it's headed "Requests".
  In both, the drawer sits in a layout-only dock after the heading.
- **A send opens the drawer.** It opens whenever the page's request log grows. The read a page sends when it opens
  (`GET /policies/<reference>` on cancel, claim and renew) counts as a send, so on those screens the drawer is already
  open, with that read as the latest request, before you press anything.
- **Bodies are indented, and only the whitespace changes.** A JSON body is laid out one key a line, and every token,
  `803.40` included, is copied exactly as received. A body that isn't JSON is shown as received. The request log
  (`#/workbench/requests`) still holds the exact wire text.
- **Claim's drawer is docked inside its section,** so it can't ride over the Record this claim button.

**Two things that look wrong but aren't N2's to fix:**
- Sell's header **Status** reads `not in this screen's data` even after a 201. That's bug-002/N3 (inv-009 #3, I9).
- A request whose fetch fails (the API is down or blocked) stays `Waiting` in the drawer. That's inv-011 I3, carried
  into N3 under HONEST-1. Don't fail an N2 step on either.

**The request shows `803.4` and the response shows `803.40`. Both are exact.** The page sends the typed amount as a JSON
number, `Number('803.40')`, so it goes over the wire as `803.4`. The API writes it back with two places. The drawer
shows each as it went. Step 4 checks both against DevTools.

Shell 1, the API, on a fresh database:

```powershell

```

Shell 2, the app:

```powershell
npm --prefix src/Uinsure.Policies.Web run trace     # the trail at HEAD -> public/trace.json (git-ignored), for the shell
npm --prefix src/Uinsure.Policies.Web run build
$env:DOCKET_API_PORT = '5081'; npm --prefix src/Uinsure.Policies.Web run preview -- --port 4171 --strictPort   # leave it running
```

Shell 3, checks and the dates:

```powershell
curl.exe -s http://localhost:5081/health/ready; ""                 # Healthy
curl.exe -s http://localhost:4171/api/health/ready; ""             # Healthy: the proxy reaches 5081
$T = [TimeZoneInfo]::ConvertTimeBySystemTimeZoneId([DateTime]::UtcNow, 'GMT Standard Time').ToString('yyyy-MM-dd')
$T61 = ([DateTime]::ParseExact($T, 'yyyy-MM-dd', $null)).AddDays(61).ToString('yyyy-MM-dd')
"T=$T T+61=$T61"                                                   # write both down: the steps use them
```

`T` is today on the UK calendar, which is the API's calendar. Type dates as `yyyy-MM-dd`. Don't run the script across
midnight.

**The request log lasts as long as the page.** The drawer, the policy view's requests and the request log page all
read one in-memory log. A reload, a new tab or a new window empties it. From step 1 to step 16, **never reload**.
Move between screens only by the links the steps name, or by changing only the part after `#` in the address bar and
pressing Enter. In DevTools Network, leave *Preserve log* unticked and type `/api/` in the filter box.

**The drawer's count is page-wide.** "Open · *n* requests" counts every request since the page loaded, not just this
screen's. The steps check the newest items, not *n*.

When you finish, stop both servers with Ctrl+C, then run `Remove-Item qa-n2.db*`.

## Notes

1. **The on-open read opens the drawer.** On cancel, claim and renew, the page reads the policy when it opens, and
   that read is a send. So the drawer is open, with that GET as the latest request, before you press anything. This
   is the behaviour the `baseline: wb-cancel` ruling covers. If you'd rather the drawer opened only on a button's
   send, that's a steer, not a defect in N2's acceptance.
2. **A renewal the API accepts can't be made live today.** A policy can't be sold backdated (SELL-2), so no policy on
   a fresh database is inside its renewal window. Step 12 sends a renewal the API refuses, and the drawer shows the
   422 exactly. The e2e `after a renewal on the renew screen …` sends on the live API, whatever the API answers.
3. **Home and the policy view have no drawer.** Neither signed-off screen draws one. Their requests show on the
   policy view's "Requests that touched this policy", which lists lines only, and in full on the request log page
   (steps 13 to 15). AC3's "every workbench screen" is tested on the four screens that send from a form: sell,
   cancel, claim and renew. If you read AC3 as covering home and the policy view too, say so at pause 2.
4. **Two known issues sit in N3, not here:** sell's Status reading `not in this screen's data` after a 201 (I9), and a
   failed fetch shown as `Waiting` (inv-011 I3). You'll see both in step 3 and in the `api-unreachable` shots.
5. **Step 17 rewrites `src/Uinsure.Policies.Web/test-results/`.** It's git-ignored. Never run it with
   `--update-snapshots`: the orchestrator writes the baselines after your ruling.
6. **What I saw and what I didn't.** I haven't run these steps. I read the expected text from `RequestsDrawer.tsx`,
   the kit's `InspectorDrawer.tsx`, `SellPolicy.tsx`, `CancelPolicy.tsx`, `RecordClaim.tsx`, `RenewPolicy.tsx`,
   `WorkbenchHome.tsx`, `PolicyView.tsx`, `RequestLogPage.tsx`, `browser.ts` and `api.ts` at 5e068f6e. I looked at
   two `-actual` shots from the gate run at 2ed982df: wb-sell `populated-1440-light` and wb-cancel
   `populated-1440-light`. The drawer counts in step 18 for `submitting` and `api-error` are read from the
   regression flows, not from a shot. Steps 6 and 12 name the rule the API should refuse under. They don't quote its
   wording.
