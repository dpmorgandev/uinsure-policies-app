## What changed in N3

- **Sell's header has a Status.** Before a sale, and after any send that didn't sell, the Status field reads
  `nothing sold yet`, with the dashed "gap" icon. On main it read the kit's default, `not in this screen's data`.
  After a 201 it reads the `status` the API returned (`Active` for a start date of today, `Pending` for a future one).
- **Cancel's header has a Status.** It reads the status of the policy the page read when it opened, and, after a
  201 cancel, the status of the re-read. On main it read `not returned`, though the page held the status.
- **A 201 sale moves focus to the answer.** The answer is the Problems note, "None. The API answered 201 and returned
  no problems. Open policy …", which sits above the form. The Send button is at the foot of the form. On main only
  the error outcomes moved focus, so a 201 left you at Send with nothing changed in view. David ruled focus, not a
  redirect.
- **A failed re-read is marked.** If the cancel answers 201 but the re-read of the policy fails, the Status reads
  `<status> (read before the cancel)` with an amber tag. On main it kept the old status, unmarked.
- **A rung receipt only prints a status it has.** The quote and cancel receipts now print only once their step is
  done, so neither can read "answered ,".
- **A rejected fetch reads as failed.** When `fetch` itself throws (nothing answered), the log entry is marked
  `failed`. The drawer draws it with a red `Problem` tag and the note "The request failed: no response came back.",
  and the request log draws `Failed`. On main both drew it as still waiting (`Waiting`, `Pending`).

**Stopping the API isn't a rejected fetch.** The browser never talks to the API directly: it talks to the app's
preview server on 4172, which proxies `/api` to 5082. With only the API stopped, Vite's proxy answers **502** with an
empty body (Vite 8.3.4, `proxyMiddleware`'s error handler). The fetch resolves, so the page reads it as a 502
problem, as it already did on main. Step 14 shows that. To reject the fetch, step 15 stops the app server as well.
The page keeps running from memory, so nothing answers it at all. Note 1 gives a second way, DevTools request blocking.

**Both header fields are marked after a failed re-read.** Review round A1 found that the **Policy status** field
read the bare old status while **Status** was marked (A1/I1). The fix, 82518511, has `CancelPolicy.tsx` work the
value out once (`statusShown`) and give it to both fields, so after a failed re-read (step 12) each reads
`<status> (read before the cancel)`. Only **Status** takes the amber tag: the kit's header id field has no tone, so
the words are the mark there. The orchestrator ruled on this in the A1 findings event in `loop.jsonl` (both fields
stay, and each is marked when the re-read fails), so the sign-off doesn't ask you about it.

**One thing I expect you'll see that N3 doesn't fix.** When a rejected request is the drawer's newest, its
screen-reader announcement reads "Request #*n* answered", though nothing answered. The kit's `InspectorDrawer.tsx`
builds the announcement from `outcome`, and N3 maps a failed entry to the `problem` outcome. Step 15 tells you where
to read it. It isn't visible on screen. It's now an N4 acceptance line in `docs/plans/active/bug-002.dag.yaml` (A1
R4), fixed there through a kit gap on `InspectorDrawer`, so the sign-off records what you hear but asks for no
ruling.

## Notes

1. **A second way to reject the fetch.** If you'd rather keep the servers up for part D, use DevTools request
   blocking. Network → right-click the `POST /api/policies` row → *Block request URL*, then press **Sell this
   policy**. The fetch rejects with `net::ERR_BLOCKED_BY_CLIENT`, and steps 15 and 16 read the same, with `Failed to
   fetch` as the error. Unblock afterwards (*More tools* → *Network request blocking*). I haven't checked whether
   the pattern also matches the longer `/api/policies/…` paths, so unblock before you send anything else.
2. **The console patch for step 12.** Paste it as one block:

   ```js
   const realFetch = window.fetch;
   window.fetch = (input, init) =>
     String(input) === '/api/policies/QA-N3-STALE' && (init?.method ?? 'GET') === 'GET'
       ? Promise.resolve(new Response('{"status":503,"title":"Service Unavailable"}', { status: 503, headers: { 'content-type': 'application/problem+json' } }))
       : realFetch(input, init);
   ```

   It works because the page's logging fetch calls the global `fetch` on every request (`app/workbench/browser.ts`).
   So the 503 still goes through the request log, and the drawer shows it. It only changes the exact read
   `GET /api/policies/QA-N3-STALE`, so the quote and the cancel still reach the API. Step 13 puts the real fetch back.
3. **"nothing sold yet" after a send that didn't sell.** The Status is the outcome of the latest send. After step 6's
   422 it reads `nothing sold yet`, though steps 2 and 4 sold two policies on this page. That's true of the last send,
   and it no longer carries `Pending` from step 4. But "nothing" can read as "nothing this session". If the wording
   should say "this send" or "not sold", that's a steer. I'd put it on U7's acceptance list, not a fix round.
4. **The drawer's announcement for a rejected request.** I read this from `kit/layouts/inspector-drawer/InspectorDrawer.tsx`.
   When the newest request isn't `pending`, the live region reads "Request #*n* answered", plus the status if there is
   one. N3 maps a rejected fetch to `problem`, so a screen reader hears "Request #*n* answered", with no status, for a
   request that got no answer. The fix is a kit line. It's an N4 acceptance line now (`bug-002.dag.yaml`, A1 R4),
   so N3 leaves it as it is.
5. **The tag colours are fixed.** Sell and Cancel draw the Status in green (`pass`) whatever the word, so `Pending`
   and `Cancelled` are green there. The policy view maps `Pending` to grey and `Cancelled` to red. The word is always
   the API's. Only the colour differs between screens. A U7 line if you want it matched.
6. **Part D ends the session.** Once both servers are stopped, everything the page sends is rejected. If you want to
   go on, restart Shell 1 and Shell 2 with their commands, and keep the tab: the log survives a server restart, but
   not a reload.
7. **What I saw and what I didn't.** I haven't run these steps. I read the expected text from `SellPolicy.tsx`,
   `CancelPolicy.tsx`, `RequestsDrawer.tsx`, `RequestLogPage.tsx`, `PolicyView.tsx`, `ProblemView.tsx`, `api.ts`,
   `browser.ts` and the kit's `PageHeader.tsx`, `InspectorDrawer.tsx`, `RequestLog.tsx` and `HttpExchange.tsx`, at
   9a5b98bc. The 502 in step 14 is from Vite 8.3.4's proxy source in this worktree's `node_modules`, not from a run.
   The Network texts (`(failed)`, `net::ERR_CONNECTION_REFUSED`, `Failed to fetch`) are Chromium's. Firefox words
   them differently. Steps 6 and 9 to 11 name what the API should answer. I haven't quoted the refund figures.
